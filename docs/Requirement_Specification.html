Project Specification

The purpose of this assignment is to create an end-to-end Smart Solar Microgrid Trading System using client-server architecture. The system features a web application for back-office administration and microgrid site operators, alongside a mobile application for solar prosumers (property owners with solar panel arrays).

a) Web Application:

  • User Management: Create web application users with two distinct roles: Backoffice and Grid Operator. Only Backoffice users have access to system administration functions, while Grid Operators access operational tools.
  • Prosumer Management: Create, update, and deactivate prosumer profiles using National Identity Card (NIC) as the primary key. Deactivated accounts can only be reactivated by a Backoffice officer.
  • Microgrid Node Management: Manage solar grid hubs, including creating new hubs with GPS location, capacity specs (kW/h), and available battery storage slots. Update schedules and deactivate nodes (deactivation is blocked if active energy reservations exist).
  • Energy Slot Reservation Management: Create, update, and cancel power trading reservations (must be scheduled within 7 days; updates and cancellations require at least 12 hours' notice).
  • User Interface: Developed using Bootstrap 5, Tailwind CSS, or React.js for a responsive appearance.

b) Mobile Application: Mobile apps must be pure Android with SQLite DB (no frameworks)

Mobile applications are intended to provide functionalities for both Solar Prosumer and grid operators.

  • Native Specs: Pure native Android with local SQLite database for local user management (no cross-platform frameworks allowed).
  • Prosumer Account Control: Prosumers register using NIC as the primary key, edit profile data, and request account deactivation.
  • Reservation & QR Dispatch: Prosumers reserve, modify, or cancel energy drop-off/charging slots. Once approved, the app generates a secure transaction QR code.
  • Dashboard & Maps: Display active/pending reservation counts, Bookings, and nearby grid nodes via Google Maps API. Additionally, user should be able to view booking history, pending booking and search booking.
  • Operator Mode: Grid Operators log into the mobile app, scan the prosumer's transaction QR code, verify server data, and finalize energy transfer business logic.

c) Web Service

  • Architecture: FAT Service pattern where all business logic resides strictly in the central API.
  • Tech Stack: C# Web API deployed on Windows IIS Server with a NoSQL server-side database (e.g., MongoDB).
  • Client Constraints: Both Web and Pure Android clients act as UI interfaces, maintaining local persistence where specified (SQLite on Android) and communicating exclusively via RESTful API calls to the central service.

The web application and mobile application should be limited to user interface functionality with Database and interact exclusively with the web service.

This system incorporates web and mobile applications that connect to a centralized web service running on IIS. Both client applications interact with the web service to access processed data and business logic. The server-side data storage utilizes a NoSQL database.

Therefore, it should develop an Android mobile application (Pure android and No frameworks) and web applications which have only interfaces to interact with Web service to facilitate data and Business logic and the NoSQL database.

High-level diagram description: Mobile app (with SQLite) and Web app both send Request/Response to the central SERVICE, which connects to MongoDB.

Project Scenario:

In this project scenario, the Backoffice team is responsible for managing the registration of solar microgrid nodes and maintaining their operational schedules. Grid operators, who can access both the web application and the mobile application, are responsible for updating battery slot availability and monitoring power trading bookings. Solar prosumers, on the other hand, can conveniently use the mobile application to reserve energy slots, modify existing reservations, and review their energy transfer history. Once a booking is confirmed, the prosumer receives a confirmation and can access the details directly on their dashboard. If circumstances change, cancellations can be easily made either through the mobile application or with the assistance of a grid operator.

This assessment has been designed using the CLEAR Framework and is levelled against the AI Assessment Scale. It is set at Level 2 — AI Planning. AI tools — chat assistants, IDE copilots and agentic coding tools — may be used only during the initial planning stage of the project: brainstorming ideas, outlining the solution, and carrying out preliminary research into the domain and the technologies involved. Anything an AI tool produces at that stage must be critically evaluated, refined and developed further by you; it is a starting point, not an answer. The actual development and implementation of the system, including the C# Web API, the native Android application, the web application and the MongoDB database, must be completed independently without AI assistance. The submitted project must reflect your own understanding, technical skills, design decisions and development effort.

Evidence of how the work was produced forms part of the assessment. You are expected to develop under version control (GitHub) with meaningful, descriptive commits, and to document your design and development decisions in the report. In your individual contribution section of the report, disclose any AI tools you used during the planning stage and include a short reflection addressing. No marks are awarded for the disclosure or the reflection itself. At the viva, however, you will be asked structured questions about your submitted work, your development decisions and your use of AI, and you must be able to explain and justify how your initial ideas became the final solution. Any code, diagram or documentation you cannot explain or modify may receive reduced or zero individual marks.
